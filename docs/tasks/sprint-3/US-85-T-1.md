# Connect scan submission form to API and display security summary dashboard

## Description
Serves User Story #85 (Full risk detection and security scoring for projects / Issue #55). This task connects the scan input forms in `frontend/src/App.tsx` to the backend scan API and implements the security summary dashboard. It implements the `GET /health` endpoint so the live monitoring system status turns healthy, calculates and displays security posture metrics (Critical, High, Medium, and Clean package counts with a visual health ratio bar), and displays the scanned project target and component breakdown.

Rendering the detailed component/vulnerability sorting table (owned by `samuelrenteria2005` in issue #70) and CycloneDX JSON download button (owned by `fromfacade` in issue #72) are out of scope.

## Specs
- Implement `GET /health` in `app/main.py` returning HTTP 200 with `{ "api": "ok", "db": "ok" }`.
- `POST /api/scan` handles form submission and validates inputs:
  - Rejects empty submissions (neither URL nor files) with HTTP 400 and descriptive error.
  - Rejects submissions containing both URL and files with HTTP 400.
  - Rejects malformed or non-GitHub repository URLs with HTTP 400.
- In `frontend/src/App.tsx`:
  - Submitting a repository URL or files calls `/api/scan`.
  - Disables form inputs and submit button while scan is running with loading feedback (`Scanning…`).
  - Displays error banners when API returns an error status.
  - Displays the active scanned target (e.g. `Target: https://github.com/...`) in the results header.
  - Provides a "Clear Results" button to reset the UI state.
- In `frontend/src/SecuritySummary.tsx`:
  - Calculates count of packages for each severity level: Critical, High, Medium, Low, and Clean (None).
  - Displays an overall Security Posture status badge (`Critical Risk`, `High Risk`, `Moderate Risk`, or `Secure`).
  - Displays a visual Dependency Health Breakdown bar indicating percentage of clean vs vulnerable dependencies.
- Automated tests in `tests/test_us_85_t_1.py` asserting all acceptance criteria with matching test names.

## Requirements
- Built using React, TypeScript, and Tailwind CSS already configured in `frontend/`.
- Must not break existing Jinja template route `/results`.
- The live `/health` monitoring badges must remain operational and report healthy.
- No new runtime dependencies.

## Acceptance criteria
1. `GET /health` returns HTTP 200 with `{ "api": "ok", "db": "ok" }`.
2. `POST /api/scan` rejects empty submissions with HTTP 400 and a descriptive error message.
3. `POST /api/scan` rejects submissions containing both a URL and uploaded files with HTTP 400.
4. `POST /api/scan` rejects non-GitHub or malformed repository URLs with HTTP 400.
5. The security summary dashboard correctly calculates counts for Critical, High, Medium, and Safe components.
6. The security summary dashboard correctly determines overall posture status (Critical Risk, High Risk, Moderate Risk, Secure).
